# DNSE OpenAPI v2 — Calling Guideline & Lessons Learned

Written for a bot that needs to build a dashboard (balances / positions / orders / NAV /
quotes) on top of DNSE's OpenAPI. Originally compiled 2026-08-03 from a live trading fleet
that has run 2 real DNSE accounts (margin + cash-only) since 2026-07-01 — every "gotcha"
below caused a real incident, not a hypothetical. Source: reference Python client
`dnse_api.py` (~365 lines) + wrapper `trading_bot/brokers.py`'s `DNSEBroker` (~370 lines).

**Review note (2026-08-04, tbot):** §1–§2, §4, §8 (signing, endpoint list, loanPackageId
requirement) cross-checked directly against `WorkingClaude/dnse_api.py`'s implementation AND
against DNSE's own official SDK (`github.com/dnse-tech/openapi-sdk`, `python/dnse/api/
client.py` + `common.py`, fetched live) — both agree on the signing-string format, and the
official SDK's `build_signature()` confirms the `headers=` attribute lists only
`"(request-target) date"` (never `nonce`, even though nonce IS part of the signed string) —
a detail easy to get backwards. One real gap found and fixed in this version: the recipe was
missing the URL-encoding step between base64-encoding the HMAC digest and embedding it in the
header (confirmed necessary by both `dnse_api.py`'s `quote(base64.b64encode(...))` and the
official SDK's own description of its signing step).
**§3, §6, §7, §9, §11 (OTP race, three cash fields, T+2 cutover timing, modify-500-quirk,
multi-account contamination) remain unverified by tbot** — these are empirical/production
claims that can't be checked against the client-wrapper code (it just passes through raw
JSON) or the official SDK (same shape — no typed response models). DNSE's hosted docs pages
for these endpoints render interactively and didn't yield field-level content via fetch.
Confirming them needs either a live account call or a rendered copy of DNSE's response
schema — tracked as an open, narrower ask-to-verify.

## 1. What DNSE OpenAPI v2 is, and how auth differs from other VN brokers

- Base URL: `https://openapi.dnse.com.vn`. Send an API `version` header (date-stamped API
  version string, e.g. `2026-05-07` — check DNSE's docs for the current value).
- No username/password login. Register once at `entradex.dnse.com.vn` -> Lightspeed API to
  get an API Key + API Secret pair. The secret is shown exactly once at registration — store
  it immediately, there is no "forgot secret" recovery, only re-issue.
- Every single request (including read-only inquiry/market-data calls) is signed with
  HMAC-SHA256 over the API Secret — there is no bearer-token session for reads.
- Placing/modifying/canceling an order additionally requires a short-lived trading-token
  obtained via OTP. Inquiry and market-data endpoints do NOT need this token.

## 2. Request signing (HMAC) — exact recipe

```
signing_string = "(request-target): {method_lower} {path}\n"
                + "date: {RFC-1123 UTC date}\n"
                + "nonce: {random hex, e.g. uuid4().hex}"
raw_signature  = HMAC_SHA256(key=API_SECRET, msg=signing_string)   # digest bytes
b64_signature  = base64_encode(raw_signature)                      # bytes -> base64 text
header_value   = url_encode(b64_signature)                         # base64 text -> URL-safe
```

**The URL-encoding step is required**, not optional — base64 output can contain `+`, `/`, `=`
characters that are unsafe inside an HTTP header value verbatim. Confirmed against both
`dnse_api.py` (`quote(base64.b64encode(mac.digest()).decode("utf-8"), safe="")`) and the
official SDK (its own docs describe the signature as "base64-encoded and then URL-escaped").

Headers on every request: `Date`, `X-Signature: Signature keyId="...",algorithm="hmac-sha256",
headers="(request-target) date",signature="<url-encoded b64 signature>",nonce="..."`,
`x-api-key`, `version`, `trading-token` (only on order place/modify/cancel).

**Note the `headers=` attribute lists only `(request-target) date`, never `nonce`** — even
though nonce IS part of what got signed. Confirmed against the official SDK's
`build_signature()`, which builds `headers = "(request-target) {date_header}"` unconditionally
and only appends nonce to the *signed string*, never to that attribute. Easy to get backwards
if implementing from the recipe alone rather than copying the header-construction code.

Other gotchas: signing string is path only — query string excluded (sign before appending
`?query=...`). `Date` must be within ~±1 minute of DNSE's clock or the signature is rejected
even if the HMAC math is correct (check NTP sync before debugging signing code). Fresh nonce
per request — never cache/reuse.

## 3. Trading-token (order placement only) — OTP flow, caching, multi-account trap

Two OTP channels: `smart_otp` (EntradeX app, 30s validity) or `email_otp` (via
`send-email-otp`, 2min validity). `POST /registration/trading-token` returns a token valid 8h
(cache with ~5min buffer).

Real incident (2026-07-08): two sub-accounts sharing the same DNSE login share ONE OTP
channel and ONE trading-token. Two processes waking at the same cron tick both requested OTP
within the same second and both polled the same inbox — classic TOCTOU race; the second got
`HTTP 500 INVALID_OTP`. If driving multiple sub-accounts under one login: serialize the
OTP-fetch-and-redeem sequence with a real lock, re-check the cached token after acquiring it.

For a dashboard-only bot (no order placement), this token is never needed at all — just don't
request it, and this whole class of problem is sidestepped.

## 4. Endpoint reference (what a dashboard actually needs)

- `GET /accounts` — list sub-accounts.
- `GET /accounts/{acc}/balances` — cash balance (see §6 — 3 different "cash" fields).
- `GET /accounts/{acc}/ppse?symbol=&price=&marketType=&loanPackageId=` — the ONLY authoritative
  "can I buy this now" answer (see §6).
- `GET /accounts/{acc}/positions?marketType=` — `total` (held) vs `sellable`/`tradeQuantity`
  (settled, released T+2 afternoon) — see §7.
- `GET /accounts/{acc}/orders?marketType=` — today's order book.
- `GET /accounts/{acc}/orders/{id}?marketType=` — one order's detail.
- `GET /accounts/{acc}/orders/history?from=&to=&pageSize=&pageIndex=` — up to 1yr, dates
  `YYYY-MM-DD`.
- `GET /accounts/{acc}/loan-packages?symbol=` — needed even for cash-only orders (§8).
- `GET /price/{symbol}/secdef?boardId=` — ceiling/floor/ref price, lot size, tick size.
- `GET /price/{symbol}/trades/latest?boardId=` — matchPrice, totalVolumeTraded.
- `GET /price/{symbol}/quotes/latest?boardId=` — best bid/offer.
- `GET /price/{symbol}/close?boardId=`, `GET /price/ohlc?symbol=&resolution=&type=`,
  `GET /market/working-dates`, `GET /instruments?...`.

Order placement (not needed for a dashboard): `POST /accounts/orders` (requires
`loanPackageId` even cash-only, §8), `PUT .../orders/{id}` (modify — see §9's HTTP 500
quirk), `DELETE .../orders/{id}` (cancel). All verified present and param-matching in
`dnse_api.py`'s method signatures.

## 5. Response-shape quirks (parse defensively)

- `balances` can come back as a bare object, a 1-element list, or nested under `stock`/
  `derivative` keys — unwrap defensively.
- Field names are inconsistent in case across responses (`availablecash`/`availableCash`) —
  look up case-insensitively / try multiple spellings.
- Market-data endpoints return per-board arrays (`G1`=round lot — the one you almost always
  want; `G4`=odd lot; `T*`=negotiated deals). Pick the `G1` row explicitly; don't take
  `rows[0]` blindly.
- `positions`: `total`/`quantity` = total held; `tradeQuantity`/`sellableQuantity` = sellable
  today — these differ whenever a recent buy hasn't settled (§7).
- Numeric fields sometimes arrive as strings — coerce defensively.

## 6. Buying power — the single most misleading part of the API

Three different "cash" fields answer three different questions:

- `availableCash` (balances) — settled cash only, excludes today's sale proceeds (T+2
  pending). Looks most like "my cash" and is the one most likely to mislead.
- `totalCash` (balances) — includes credited-but-unsettled sale proceeds. Correct input for
  NAV (`NAV = totalCash + market value of positions - margin debt`), wrong for a same-day
  "can I buy" check alone.
- `pp0Buy`/`qmaxBuy` (ppse) — the broker's own answer to "how much/many shares of X can I buy
  right now at price P," already factoring in same-day sale proceeds AND the margin limit of
  the `loanPackageId` passed. The ONLY field that should gate a buy decision.

Real incident: sold shares at 09:42; at 09:56 `availableCash` was completely unchanged while
`pp0Buy` already reflected the just-sold proceeds — DNSE lets a cash account re-buy with
same-day sale proceeds well before T+2 settlement completes. A dashboard showing "available
cash" using `availableCash` alone will look stale to a user who just sold something — surface
`ppse`'s `pp0Buy` alongside it, labeled distinctly ("settled cash" vs "buying power now").

Also: when a buy fills on a cash account, DNSE moves the purchase amount from `totalCash`
into a `secureAmount` (escrow) field within minutes — money already committed to shares held
(counted in position market value), not money that vanished. Don't add `secureAmount` back
into a cash total — that double-counts against the position's market value.

## 7. Settlement mechanics (T+2)

- Shares bought on day T become sellable starting the AFTERNOON session of T+2, not from
  market open. Verified: shares bought Thursday were still rejected with `HTTP 400: Trade
  quantity not enough` through Monday (T+2) morning, succeeded once the afternoon session
  started. Compute "sellable" from the position's own sellable field, not from "T+2 has
  passed = sellable" — the cutover is mid-day, not midnight.
- Cash-side settlement is looser than share-side (see §6) — same-day sale proceeds are
  usable for buying same-morning via `ppse`, even though the shares that generated them
  followed the T+2 timeline on the way in. Don't conflate the two.
- A balance snapshot is only meaningful for NAV/cash display if its timestamp is newer than
  the account's most recent fill of the day — otherwise label it "as of {snapshot time}," not
  "current."

## 8. `loanPackageId` — required on EVERY order, even cash-only

- Omitting it fails with `HTTP 400: loanPackageId is required` — even for a plain cash order
  with no leverage intent (hit twice in production). Confirmed against `dnse_api.py`'s
  `place_order()`, which only attaches `loanPackageId` conditionally
  (`if lp is not None`) — meaning a client with no default configured and no explicit override
  would silently omit the field, reproducing exactly this failure mode. Don't rely on a
  default being set; pass one explicitly if there's any doubt.
- An account's one "default" loan-package ID isn't universally valid across boards — call
  `GET /accounts/{acc}/loan-packages?symbol=X` first, check the default appears in the valid
  list for that specific symbol, pick another valid one (prefer `type == "N"` cash-type over
  `type == "M"` margin-type if no leverage intent) if not.
- Fail-safe direction: if you can't determine a valid package, send the account's default
  anyway rather than omitting the field — a well-formed request that gets business-rejected
  is safer than one that's structurally invalid.

## 9. Order-placement quirks (only relevant if placing/modifying orders)

- `modify_order` returns HTTP 500 `REMOTE_SERVER_ERROR` on SUCCESS. DNSE implements "modify"
  server-side as cancel-old + place-new, and the response for that internal re-place comes
  back as an error even when the modify worked. Don't treat this 500 as failure — re-poll the
  order book a second later and look for the new order.
- Don't round quantities down to zero for odd lots. Odd lots (<100 shares) are placed exactly
  like round lots via the same order endpoint — DNSE needs no special parameters for them.

## 10. Idempotency — treat the broker's live order book as ground truth

DNSE has no client-side idempotency-key mechanism to dedupe. A process-level lock only
prevents two runs from overlapping — it does nothing for one run dying mid-write after the
external call already succeeded. For a dashboard, the practical takeaway is simpler: always
render from a fresh `GET /accounts/{acc}/orders`/`positions` call, don't reconstruct "what
should be true" from a local order log alone.

## 11. Multi-account gotchas

- Any locally-written log file keyed only by date (not by account) will silently interleave
  records from multiple accounts once a second account goes live the same day. Always tag
  every persisted record with the account identifier at write time, filter by it on every
  read.
- DNSE responses don't self-identify which account they're for (e.g. a `balances` response has
  no account field) — the account context comes from which URL you called. Tag it yourself
  before persisting if fanning out across multiple accounts.
- Sub-accounts under the same login share one OTP channel/trading-token (§3) — irrelevant for
  pure reads.

## 12. Error handling

- Non-JSON response body -> treat as an error with the raw HTTP status + truncated text.
- `HTTP >= 400` -> raise, carrying the parsed `message`/`error` field — don't silently swallow
  and return an empty/default value.
- Network/timeout errors on inquiry endpoints should degrade to "unknown" (`None`) rather than
  a fabricated fallback — a caller that can't tell "the broker said no" from "I couldn't ask"
  may make an unsafe decision.
- Set a real request timeout; retry idempotent reads, but never blindly retry an
  order-placement call without first checking the order book for whether it already went
  through.

## 13. Freshness discipline

Any same-day figure (today's price, position, cash) must come from the live DNSE API call,
never from an overnight-synced warehouse copy — a nightly sync necessarily reflects
yesterday's close. If both a live and a cached/historical path exist, make the split explicit
and label it in the UI ("live" vs "as of {last sync}") — don't let a dashboard silently mix
them.

## 14. Quick-reference checklist for a dashboard build

- Sign every request per §2 (don't forget the URL-encoding step); verify host clock is
  NTP-synced before debugging signature rejections.
- Never request a trading-token unless actually placing/modifying/canceling orders.
- Parse `balances` defensively (list-or-object, possible nesting, case-insensitive lookup).
- Show `availableCash` and `pp0Buy` (via `ppse`) as two different, separately labeled numbers.
- Compute NAV from `totalCash` (not `availableCash`) + position market value - margin debt;
  don't add `secureAmount` back in.
- Show position "sellable" quantity from the position's own sellable field, not a "T+2 has
  elapsed" date calculation.
- Pick the `G1` board explicitly when reading quotes/trades for a symbol.
- Cross-check a balance snapshot's timestamp against the day's latest order fill before
  labeling it "current."
- If showing multiple accounts: tag every persisted record with the account identifier at
  write time.
- Always render order/position state from a fresh API call.
- Treat any same-day figure as DNSE-live-only; never source it from an overnight batch copy.
